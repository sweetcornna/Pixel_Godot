## A-1：API 接受任意合规尺寸 —— ❌ 证伪

**这是本轮最严重的发现。**

端点**完全不理会 `size` 参数**，且**不报错** —— 它返回一个与请求无关的尺寸。

| 请求 | 实际返回 | 长短边比是否保持 |
|---|---|:---:|
| 2048×1024 | 1536×1024 | ✗ |
| 2048×1024（第二次） | 1774×887 | ✓ |
| 1024×1024 | 1254×1254 | ✓ |
| 1536×1024 | 1254×1254 | ✗ |
| 1024×1536 | 1536×1024 | ✗ |
| 1536×1536 | 1536×1024 | ✗ |
| 2048×1536 | 1254×1254 | ✗ |

规律：**所有返回图的总像素数都≈ 1,573,000**（1254² = 1,572,516 · 1536×1024 = 1,572,864 · 1774×887 = 1,573,538）。
即后端按固定像素预算出图，长短边比只是**有时**跟随请求。同一请求两次返回不同尺寸 ——
**非确定性**。

### 为什么这条比"报错"更危险

固定网格切分假设"返回图 = 请求的物理尺寸"，于是按绝对偏移 512px 硬切。
现在返回 1536×1024 而代码按 2048×1024 切 —— **每一帧都错位，且不抛任何异常**。
这是又一个静默失败，而且比帧序乱序更致命（帧序乱序至少每帧本身是完整的）。

### 应对（已按 PLAN 的「证伪后应对」执行）

1. **切帧改为按比例，而非按绝对像素**：格线取 `col/cols × 实际宽度`。
   只要模型把网格铺满画布，比例切分就成立 —— 本轮实测 4 条格线全部干净。
2. **`size` 仅作为长短边比的表达**，不再当作尺寸契约。
3. **Manifest 必须记录实际返回尺寸**，否则 `process` 无法离线复现切帧。
4. 新增验证项：返回尺寸的长短边比与请求不符时告警（格子会变形，
   下采样到 32×32 会带来非等比压缩）。

> ⚠️ **待确认**：`1254×1254` 不是任何已公开的 OpenAI 图像尺寸档位。
> 高度怀疑是**该代理端点**没有透传 `size`，而非 `gpt-image-2` 本身的行为。
> 若换用官方端点，本条结论需重测。但**按比例切分在两种情况下都正确**，
> 所以这个改动无论如何都该做。

## A-2：一次调用产出 N 个姿势不同的格子 —— ⚠️ 有条件成立

### 第一轮：整体描述 → 失败

prompt 用 PLAN §8 的标准约束清单（`one complete animation cycle` / `exactly 8 distinct poses`）。

结果：**8 个格子都画出来了，但 8 个姿势几乎一样** —— 全是站立，腿部基本不动。
掩膜轮廓叠上去几乎重合。这会触发「相邻帧变化：不得全部近似静止」检查。

相邻帧差异：8.2% / 23.8% / 25.7% / 7.5% / 3.3% / 30.3% / 26.3% / 7.5%
（max/min = **9.2**，毫无循环节奏可言）

### 第二轮：逐帧显式指定姿势 → 成功

把每一格该画什么写死（CONTACT / DOWN / PASSING / UP × 2 轮，
并明确"这是走路动画，不是八张站立肖像"），得到真正的走路循环：
迈步幅度、腿部交叉、身体起伏都正确。

相邻帧差异：26.4% / 13.1% / 25.0% / 9.2% / 25.2% / 12.3% / 22.9% / 8.9%
（max/min = **3.0**，且呈规整的交替节奏）

### 影响

**Prompt Compiler 必须为每个动作内置逐帧姿势模板**，不能只给整体描述。
这是 Sprint 4 的一项实质性范围增加：`idle` / `walk` / `attack` / `hurt` / `death`
各需要一套按帧数档位（4/6/8/9/12）展开的姿势序列文本。

## A-3：模型遵守从左到右、从上到下的帧序 —— ✅ 成立

第二轮样本中帧序正确：第 1、5 格是最大迈步（一个周期的起点），
第 3、7 格双腿交叉于身体正下方 —— 与 prompt 指定的顺序一致。

### 但帧序连续性检查的判据是错的

PLAN §9.2 写的是"相邻帧差异应大致均匀；突变点数 ≤ 1"。
实测**正确**的走路循环差异序列是 `26 / 13 / 25 / 9 / 25 / 12 / 23 / 9` ——
**规整地交替**，不是均匀。原因很直白：CONTACT→DOWN 是大幅形变，
DOWN→PASSING 是小幅过渡，本来就该一大一小。

按"均匀"判据，这个完全正确的循环会被判为多个突变点 —— **验证器会误报到被关掉**。

建议改为：对差异序列做**周期性**检测（相邻同奇偶位置的差异应接近），
或仅检测"单点离群"（某一个差异远大于其左右邻居的均值）。

## A-4：姿势不跨越格线 —— ⚠️ 有条件成立

| | 第一轮（8% 边距要求） | 第二轮（12% 边距要求） |
|---|---|---|
| 竖格线 1 | 干净 | 干净 |
| 竖格线 2 | 干净 | 干净 |
| 竖格线 3 | ★ 364 px 越界 | 干净 |
| 横格线 1 | 干净 | 干净 |
| 实测最小边距 | **0.0%** | **7.9%** |

结论：**prompt 里要 8% 只能拿到 0%，要 12% 才能拿到 7.9%。**
模型把边距要求当成软约束，实际执行大约打七折。

**应对**：prompt 里的边距要求写 12%，验证阈值仍按 8% 判。

## A-5：纯洋红键控干净可用 —— ⚠️ 部分成立

### 坏消息：从来不是精确的 `#FF00FF`

| | 第一轮 | 第二轮 |
|---|---|---|
| 精确 `#FF00FF` 像素占比 | **0.00%** | ~0.2% |
| 背景实际均值 | `#F204EA` | `#F304EF` |
| 与 `#FF00FF` 的距离 p50 | 24 | 19 |
| 背景唯一颜色数 | 345 / 40,960 px | 348 / 42,576 px |

**ADR-004 第 1 档「默认键控色精确色键」在真实数据上命中率为零。**
按精确匹配实现的话，抠图会一个像素都抠不掉。

### 好消息：宽容距离键控非常干净

距离直方图上背景簇与前景簇之间有一条**极宽的空谷**：

```
 20–30  1,033,997  ← 背景簇
 30–40     17,028
 40–60      4,059
 60–80      1,650   ← 空谷，仅 0.76% 像素落在 40–200 区间
 80–100     1,274
100–130     1,715
130–160     1,330
160–200     1,976
200–260     51,167  ← 前景簇
260–340    304,663
```

Otsu 自动阈值（本例 165）落在谷中，产出的掩膜**干净到可以直接用**：
8 个轮廓完整分离、无孔洞、无噪点、角色内部零误伤。

### 影响

1. **删掉「精确色键」这一档**，把「宽容颜色距离键控 + Despill」提升为**默认主路径**。
   阶梯相应从 6 档缩为 5 档，`fallback_stage` 语义需要重新编号。
2. 阈值应当**每张图自动求解**（Otsu 或谷底检测），不要写死常数 ——
   两轮样本的背景距离 p50 就差了 24 vs 19。
3. 落在 40–200 区间的 0.76% 像素是抗锯齿光晕，Despill 的目标就是它们。
4. 形态学运算必须**先补边再做**：`scipy` 的腐蚀在图像边界按"外部为前景"处理，
   会把最外一圈背景吞掉，导致从边缘泛洪的种子为空集。
   （这个坑在本轮调试中真实踩到了。）

## A-7：`up`（背面）身份一致性 —— ✅ 成立（Sprint 4 补测）

本轮只跑了 `down` 方向，`up` 留到了 Sprint 4。补测结论：**成立，而且背面比正面更好。**

同一个 seed 生成的 `walk_down` 与 `walk_up` 对比：

| | `walk_down` | `walk_up` |
|---|---|---|
| 返回尺寸 | 1536×1024（比例被改成 1.5:1） | 1774×887（保住 2:1） |
| 单元格越界 | ★ 3 个连通域跨格，最小边距 0.0% | 干净 |
| 锚点漂移 | 0.5 px | 0.0 px |
| 身份一致性 | 好 | 好 |

背面缺少正面细节（脸、正面配饰），反而**少了漂移的机会** ——
八帧的斗篷、发色、剑的位置全部一致。

PLAN §9.1 给 `up` 方向的轮廓类阈值 ×1.3 修正，依据是"背面天然更不稳定"。
这个假设**没有被本轮数据支持**。修正系数应在 Sprint 5 校准阈值时用真实分布重估，
不要凭直觉保留。

### 附带发现：长短边比被改动会诱发越界

两次调用的差别很说明问题：`walk_up` 保住了请求的 2:1，切出来的格子接近正方，干净；
`walk_down` 被改成 1.5:1，4×2 网格的格子变成 384×512（宽高比 0.75），
横向被压扁 —— 模型按"方格"构图，拿到的却是竖长格，于是剑尖越过了竖格线。

成品帧上能直接看到损伤：第 3、7 帧右侧各漂着一截断剑，那是邻格越界后被切进来的。

**推论**：`aspect_mismatch`（[A-1](#a-1api-接受任意合规尺寸--证伪) 引入的量）
不只是"记录一下"的信息，它是**越界的先行指标**。Sprint 5 的验证报告应当把它
与 `cell_overflow` 关联呈现，让"为什么这次越界了"一眼可答。

## 记录到的模型失败模式

PLAN 要求"至少记录 3 类模型失败模式"。实测到 5 类：

| # | 失败模式 | 严重度 | 能否本地修复 |
|---|---|---|---|
| 1 | **返回尺寸与请求无关**，且不报错 | 致命 | 可（改比例切分） |
| 2 | **动作退化为静止** —— 给整体描述时 8 帧全是站姿 | 高 | 否，必须重生成 |
| 3 | **姿势跨格线** —— 边距要求打七折执行 | 致命 | 否，必须重生成 |
| 4 | **背景不是精确键控色** —— 恒定偏移约 20 个颜色距离 | 中 | 可（宽容阈值） |
| 5 | **脚底不对齐统一基线** —— 实测极差 9~10%（约 40 px） | 高 | 可（bottom-center 对齐） |

补充观察：**模型把两行当成两组来画**。第 0 行与第 1 行的脚底基线均值
系统性相差 7%（91.6% vs 84.0%），行内则一致。多行网格值得单独关注。
