# ADR-005：CLI 是核心，MCP 与 Skill 是适配层

- **状态**：已接受
- **日期**：2026-07-29
- **相关**：[ADR-001](ADR-001-manifest-first.md) · [PLAN §6](../PLAN.md)

---

## 背景

本项目的目标形态是"可安装到 Codex / Claude Code 等 Agent 环境的 Skill"。
最直接的实现是把能力直接做成 MCP 工具，让模型调用。

但这引出一个架构问题：**核心实现应该放在哪一层？**

- 方案一：核心逻辑在 MCP Server 中，CLI 只是薄封装。
- 方案二：核心逻辑在 CLI / Python 库中，MCP 只是薄适配层。

同时还有一个接口设计问题：**应该向模型暴露多少个工具？**
像素处理涉及十几个模块（切帧、键控、despill、裁剪、缩放、对齐、量化、清理、合成……），
把它们逐个暴露给模型，理论上给了模型最大的灵活性。

## 决策

**核心实现在 CLI / Python 库。MCP 与 SKILL.md 都是薄适配层。**

**并且：向模型暴露的工具数量必须刻意收敛。**

| 接口面 | 数量 | 内容 |
|---|:---:|---|
| **CLI** | **9** | `init` `doctor` `plan` `create-character` `create-animation` `process` `validate` `repair` `export` |
| **MCP** | **6** | `create_character` `create_animation` `create_asset_pack` `validate_asset` `repair_asset` `export_asset` |

MCP 不暴露 `init` / `doctor` / `plan` —— 这三个是运维与调试命令，对模型没有语义价值。

`SKILL.md` 的职责是把用户自然语言映射到这些**稳定命令**，
而**不是**让 Agent 自由组合底层脚本。

## 理由

### 为什么核心在 CLI

1. **可测试性。** CLI 命令可以在 CI 中直接调用并断言产物，MCP Server 需要额外的协议层才能测试。
2. **可调试性。** 出问题时开发者能直接在终端复现，不需要经过 Agent。
3. **不绑定 Agent 环境。** 用户可以在脚本、Makefile、CI 中使用，不必安装任何 Agent。
4. **MCP 协议会变，Python 函数不会。** 把核心押在演进中的协议上是不必要的风险。
5. **9 个 CLI 命令中有 5 个不调用 API**（`init` `doctor` `plan` `process` `validate` `export` 中的大部分），这个离线迭代循环是开发效率的核心，它天然属于命令行而非 Agent 交互。

### 为什么工具数量必须收敛

向模型暴露几十个像素级工具有三个具体代价：

| 代价 | 说明 |
|---|---|
| **上下文开销** | 每个工具的 schema 都要进上下文，几十个工具的定义可能比任务本身还长 |
| **选错工具的概率** | 工具越多，模型选错的概率越高，且错误难以察觉 |
| **顺序错误** | 像素处理有严格的顺序依赖（despill 必须在量化之前、越界检测必须在切帧之前）。让模型编排这个顺序，等于把确定性流程交给不确定性组件 |

第三点最关键。整个项目的立论就是"**AI 只生成视觉原料，本地程序负责所有需要精确性的操作**"。
把处理顺序交给模型编排，等于在架构层面推翻这个立论。

因此 MCP 层的职责是**收敛**，不是镜像 CLI。6 个工具对应 6 个完整的业务动作，
每个工具内部的流程都是写死的。

### 为什么 CLI 是 9 个而 MCP 是 6 个

这不是不一致，而是两个接口面服务于不同使用者：

- **CLI 的使用者是开发者**，需要 `doctor` 排查环境、需要 `plan` 在执行前预览任务。
- **MCP 的使用者是模型**，只需要"做一件完整的事"的语义动作。

## 后果

**正面**

- 核心逻辑有完整的测试覆盖，不依赖 Agent 环境。
- 用户可以在任何环境使用（CLI / Python 库 / MCP / Skill）。
- MCP 协议演进时只需改适配层。
- 模型的上下文开销与出错概率都被压到最低。

**负面**

- 模型失去了细粒度控制能力。例如用户说"只重新量化一下调色板"，模型无法直接调用量化工具。缓解：这类需求通过 `repair_asset` 的参数表达，或引导用户直接用 CLI。
- 需要维护两套接口定义（CLI 参数 + MCP schema）。缓解：两者都从同一份 Pydantic 模型生成。
- `create_asset_pack` 在 MCP 中存在但在 CLI 中没有独立命令（由 `create-character` 批量调用实现）。这是刻意的：批量是模型侧的常见诉求，但在 CLI 侧用 shell 循环更自然。

## 备选方案

**A. 核心实现在 MCP Server，CLI 薄封装**
被否决。测试与调试都更困难，且把核心押在演进中的协议上。

**B. 暴露细粒度像素工具（20+ 个）给模型**
被否决。上下文开销、选错概率、顺序错误三重风险，且与项目立论冲突。

**C. MCP 完全镜像 CLI 的 9 个命令**
被否决。`init` / `doctor` / `plan` 对模型无语义价值，只会增加上下文开销和误选概率。

**D. 只做 Skill（SKILL.md + 脚本），不做 MCP**
被否决（暂时）。Skill 依赖 Agent 读取 Markdown 并自行组合命令，可靠性低于结构化的工具调用。但 MCP 排在 Sprint 9，MVP 阶段确实只有 CLI + SKILL.md —— 这个顺序是刻意的，先保证核心可用。
