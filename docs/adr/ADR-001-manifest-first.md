# ADR-001：Manifest 驱动而非脚本驱动

- **状态**：已接受
- **日期**：2026-07-29
- **相关**：[ADR-002](ADR-002-provider-abstraction.md) · [ADR-005](ADR-005-cli-core-mcp-adapter.md) · [PLAN §5.2](../PLAN.md)

---

## 背景

像素资产生成天然是多步骤流水线：生成 → 切帧 → 抠图 → 裁剪 → 缩放 → 对齐 → 量化 → 验证 → 导出。

最直接的实现方式是把这些步骤串成一个脚本，一次跑完。但这种做法在本项目的场景下有三个致命问题：

1. **生成层不可复现**（见 [PLAN §2.7](../PLAN.md)）。图像生成没有 seed 参数，同一 prompt 每次结果不同。一旦中途失败，重跑整条脚本就意味着全部重新生成，且拿到的是一套不同的图。
2. **失败是常态而非例外**。模型在角色一致性和精确构图上会持续失败。一个 20 任务的角色包，几乎不可能一次全过。
3. **人工审核必须能介入**。canonical seed 的批准是唯一的人工闸门，脚本式流水线无法在中间停下来等人。

## 决策

**引入 `asset-manifest.json` 作为资产的唯一真实来源（single source of truth），所有流水线阶段都读写 Manifest，而非互相传递内存状态。**

具体约束：

- 每个 `(asset, action, direction)` 三元组是一个独立 Job，有独立状态（见 [PLAN §5.3](../PLAN.md)）。
- 任何阶段的产物都落盘，并在 Manifest 中登记路径。
- **原始生成图永不覆盖**（`source/` 目录）。
- **所有导出文件必须能仅凭 Manifest + `frames/` 完整重建。**
- Manifest 携带 `schema_version` 与 `pipeline_version`，前者管兼容，后者管溯源。

## 理由

Manifest 把"流水线状态"从进程内存中提取到磁盘上，直接换来四项能力：

| 能力 | 没有 Manifest | 有 Manifest |
|---|---|---|
| 断点续跑 | 重跑整条链，且拿到一套不同的图 | 只跑失败的 Job |
| 离线迭代 | 改一行处理代码要重新生成 | `pixel-asset process` 完全离线重跑 |
| 人工闸门 | 无法中途暂停 | `awaiting_approval` 是一个正常状态 |
| 局部修复 | 只能整体重来 | Repair Planner 精确定位最小失败单元 |

第二项尤其重要：CLI 的 9 个命令中有 5 个完全不调用 API（见 [PLAN §6.1](../PLAN.md)），
这不是巧合，而是 Manifest-first 的直接结果。开发期绝大部分迭代都发生在处理层和验证层，
如果每次都要重新生成图像，不但循环极慢，而且每次拿到的输入都不一样，根本无法判断改动是否有效。

## 后果

**正面**

- 断点续跑、离线重跑、局部修复三项能力都成为自然结果而非额外功能。
- 验证与导出都是 Manifest 的纯函数，易于测试。
- 缓存命中与跳过重生成都建立在 Manifest 记录之上。

**负面**

- 增加了 Schema 设计与版本迁移的负担（已在 [PLAN §5.4](../PLAN.md) 中给出策略）。
- 磁盘占用显著增加 —— `source/` + `intermediate/` + `frames/` + `sheets/` + `exports/` 会有大量中间产物。接受这个代价：中间产物是离线重跑与失败归因的前提。
- 每个阶段都要读写 JSON，性能低于纯内存流水线。在本场景下无关紧要 —— 瓶颈永远是 API 调用延迟。

## 备选方案

**A. 脚本式流水线（一次跑完）**
被否决。无法支持断点续跑与人工闸门，且每次迭代都要重新生成一整套图。

**B. 数据库（SQLite）存储状态**
被否决（暂时）。JSON 文件对用户可读、可手工编辑、可进 git、可直接贴给 Agent 看，这些属性在本项目中比查询能力更重要。若未来批量规模增长到数千资产，可在 `storage/` 层内部替换为 SQLite 而不改变对外契约。

**C. 内存状态 + 崩溃时快照**
被否决。快照的一致性难以保证，且无法支持"改代码后离线重跑"这个核心开发循环。
