## 为什么推翻「固定网格切分」

初版拒绝"自动帧识别"的理由是：失败模式不可预测，且会让"生成错误"与"识别错误"
无法区分，而整个修复机制建立在能准确归因的前提上。

**这个理由针对的是开放式帧识别** —— 不知道有几帧、要从像素里推断出来。
但本项目的**帧数始终是已知的**（prompt 里写死、request 里声明）。
于是问题从"推断有几个 sprite"降级为"定位 N 个已知目标"，
约束强得多，失败模式也可判定：找不到 N 个就明确报错，而不是猜一个数。

### 代价是实测出来的，不是推演的

`walk_down` 的一次真实产出：8 个姿势彼此**完全分离、毫无损伤**，
只是整体相对假想格线右移了一点。固定格线切分把第 3、4 格的剑尖切给了隔壁格，
验证器报「3 个连通域跨格 · fatal · 必须重生成」。

然后修复器重生成了三次 —— **三次都是同样的布局**，因为根因不在随机性上
（端点稳定地把 2:1 改成 1.5:1，格子被压扁）。我在拿一个**不存在的缺陷**烧配额，
而且四方向里有一个方向永远出不来合格产出，MVP 门槛直接达不到。

换成连通域抽帧后，同一张图干净地分出 8 个 sprite：**0 重叠、0 碎片、0 告警**。

### 判据错在哪

`cell_overflow` 初版衡量的是「**模型的布局是否符合我假设的网格**」，
而真正该问的是「**sprite 有没有被切坏**」。这是两件事，只有后者是缺陷。

现在的判据是：能否用连通域分离出 `frames` 个 sprite。分不出来才是真的坏了
（姿势粘连成一片、或模型画的数量不对），此时本地补不回被切掉的像素，只能重生成。

## 抽帧算法

照搬 `hatch-pet` 的做法，并从一维横条推广到二维网格
（gpt-image-2 的 3:1 长短边比约束让 8 帧横条 8:1 不可行，必须留在二维网格生成）：

1. 色键 → 前景掩膜 → 连通域标注
2. **按面积取正好 N 个 seed**（≥ 最大面积 20% 的为候选，不足则取面积前 N）
3. **碎片按中心距离就近吸附**到 seed 上（断开的剑尖、飘带）
4. 放进**共用视口**：视口宽取所有 sprite 的最大宽、垂直范围取公共上下界

第 2 步的关键是**不使用任何间隙阈值**。我先按间隙聚类试过一版，
在姿势疏密不均时整片聚错（8 个 sprite 被聚成 2 个）。帧数已知时按面积取 seed
是更强的约束。

第 4 步对应 `hatch-pet` 的 `stable-slots`：逐帧各自裁到自己的包围盒再缩放，
每帧缩放比例不同，播放起来角色**一大一小地跳**。共用视口保住帧间的相对缩放与站位。

四种抽帧方式，默认 `auto`：

| 方式 | 做法 | 何时用 |
|---|---|---|
| `components` | 连通域定位，找不到 N 个就报错 | 要求严格时 |
| `auto` | 先试 `components`，失败退回 `stable_slots` | **默认** |
| `stable_slots` | 等分切格 + 共用视口 | 连通域粘连时 |
| `slots` | 等分硬切（原固定网格行为） | 仅作对照 |

## 保留下来的部分

「**网格化生成**」这一半没有变，且仍然成立：

- 因 API 尺寸约束无法直接请求 32×32 或长条，必须生成大尺寸二维网格再本地缩小。
- 帧数只能取能映射到合规物理尺寸的档位。
- 帧序固定为从左到右、从上到下，并写进 prompt。
- prompt 要求 12% 边距（判定按 8%）。

变的只是**切帧方式**：从"按格线硬切"变成"按连通域定位、格线仅作退化兜底"。

## 背景

`gpt-image-2` 的输出尺寸受四条硬约束限制：

| 约束 | 值 |
|---|---|
| 宽高均为 16 的倍数 | — |
| 长边 / 短边 ≤ 3 | — |
| 总像素数 | 655,360 ≤ N ≤ 8,294,400 |
| 最大单边 | ≤ 3840 px |

这意味着**无法直接请求 `32×32` 的单帧，也无法请求 `8×1` 的长条动画带**（比例 8:1 超限）。

因此动画必须以"大尺寸二维网格"的形式生成，再在本地切分并缩小。接下来的问题是：
**切分时如何确定每一帧的边界？**

两种思路：

- **自动识别**：分析图像内容（连通域、空白列检测、边缘检测）推断帧边界。
- **固定网格**：预先约定 N×M 网格与单元格尺寸，按几何位置硬切。

## 决策

**采用固定网格切分：网格的行列数在请求发出前就已确定，切分时不做任何内容分析。
但格线位置按实际图像尺寸的比例计算，而非按绝对像素偏移。**

| 帧数 | 网格 | 期望物理尺寸 | 期望长短边比 | 名义单元格 |
|---:|---:|---:|---:|---:|
| 4 | 2×2 | 1024×1024 | 1.00 | 512×512 |
| 6 | 3×2 | 1536×1024 | 1.50 | 512×512 |
| 8 | 4×2 | 2048×1024 | 2.00 | 512×512 |
| 9 | 3×3 | 1536×1536 | 1.00 | 512×512 |
| 12 | 4×3 | 2048×1536 | 1.33 | 512×512 |

> ⚠️ **"期望"两个字是 Sprint 0 加上去的，不是修辞。**
>
> 实测该端点**不保证按请求尺寸返回，且不报错**：同一个 `2048×1024` 请求，
> 两次分别返回 `1536×1024` 与 `1774×887`；`1024×1024` 返回 `1254×1254`。
> 所有返回图的总像素都≈ 157 万，长短边比只是**有时**跟随请求。
>
> 因此 `size` 参数只承担两件事：**表达期望的长短边比**、以及**本地合规自检**。
> 它不是尺寸契约。

配套的四条强制约束：

1. **切分必须按比例**：格线取 `col / cols × 实际宽度`。
   按 512px 绝对偏移去切一张 1774×887 的图，每一帧都会静默错位 ——
   这比帧序乱序更致命，因为连单帧本身都是残缺的。
2. **帧序固定为从左到右、从上到下**，并写入 prompt（[PLAN §2.3.1](../PLAN.md)）。
3. **prompt 里的边距要求写 12%，验证阈值按 8% 判**。
   实测模型把边距要求打约七折执行：要 8% 只拿到 0%，要 12% 才拿到 7.9%
   （[Sprint 0 / A-4](../sprint-0-report.md)）。
4. **编辑画布不使用 mask** —— seed 作为参考图传入，空白网格作为 base image（[PLAN §2.6](../PLAN.md)）。

## 理由

### 为什么不用自动识别

自动识别的失败模式是**不可预测的**：

- 姿势之间距离过近 → 被识别为一帧
- 单帧内有断开的部件（挥出去的剑、飞散的粒子）→ 被识别为两帧
- 角色本体与背景色接近 → 边界检测失效
- 识别出的帧数不等于请求帧数 → 无法判断是模型画错了还是识别错了

最后一条是致命的：**自动识别会让"生成错误"与"识别错误"无法区分**，
而本项目的整个修复机制（[PLAN §9.3](../PLAN.md)）建立在能够准确归因的前提上。

固定网格的失败模式则是**可预测且可检测的**：姿势跨格。这可以在切帧**之前**
通过检测跨越格线的连通域来发现，并归因为"模型构图错误"，交给 Repair Planner 重生成。

### 为什么名义单元格是 512×512

- 512 是 16 的倍数（满足 API 尺寸约束的必要条件，用于构造合规的请求尺寸）。
- 512×512 的单元格给模型足够空间画出细节，缩小后细节自然坍缩为像素块。

> **初版还有第三条理由，Sprint 0 之后不再成立**：
> "512 → 32 是精确的 16 倍下采样，最近邻缩放不产生任何中间色"。
>
> 这条依赖单元格真的是 512。实测返回 `1774×887` 时，4×2 网格的实际单元格是
> `444×444`；返回 `1536×1024` 时是 `384×512`（还不是正方形）。
> `444 / 32 = 13.875` 不是整数 —— 最近邻下采样会让有些"像素块"占 14 个源像素、
> 有些占 13 个，表现为像素大小不匀。
>
> 缓解路径（Sprint 3 落地时验证）：先裁剪到内容边界，再把**内容**缩放到逻辑尺寸，
> 而不是缩放整个单元格。裁剪后的内容尺寸本来就是任意的，与单元格是不是 512 无关，
> 所以这条路不依赖被推翻的前提。残留的不匀由 `pixel_cleanup` 与
> `palette_quantize` 兜底。**这是 Sprint 3 的一项已知风险，不是已解决问题。**

### 为什么不用 mask 保护第一格

直觉上应该把 canonical seed 直接贴进第一格，并用 mask 保护它不被重画。否决理由：

GPT Image 的 mask 是**提示性约束，不保证精确遵循边界**。用它保护第一格既不可靠，
又会让模型把注意力放在边界处理上而非身份一致性上。把 seed 作为纯参考图传入，
模型对身份的保持效果更稳定。

代价是第一格也是重新生成的，因此第一格同样要参与身份漂移校验 —— 这个代价可以接受。

同一理由也适用于修复阶段：[PLAN §9.3](../PLAN.md) 明确不把蒙版局部编辑作为主要保障手段。

## 后果

**正面**

- 切帧是**纯几何运算，100% 确定性**，golden image 测试可完全覆盖，成功率可以作为硬性指标（100%，见 [PLAN §10.5](../PLAN.md)）。
- 失败归因清晰：切帧永远不会出错，出错的只可能是生成构图。
- 帧数由请求决定而非由识别结果决定，"帧数不匹配"成为一个明确的验证项。

**负面**

- **对模型构图的要求更高** —— 模型必须把姿势画在格内。这是本方案最主要的风险（原假设 A-4）。
  Sprint 0 实测：prompt 要 8% 边距时**跨格发生了**（一条格线上 364 px 越界），
  要 12% 时四条格线全部干净、实测最小边距 7.9%。因此边距要求已上调为 12%。
- 姿势跨格时无法本地补救，只能重新生成整个网格。
- 网格布局固定后，帧数只能取表中的档位。非标准帧数（如 5 帧、7 帧）需要向上取整并留空格，或调整为邻近档位。
- **实际单元格尺寸不可预知**（A-1），因而不再有"整数倍下采样"的保证，
  见上文「为什么名义单元格是 512×512」。

**缓解**：跨格频繁时按顺序尝试：继续加大 prompt 边距要求 → 加大单元格留白（牺牲有效分辨率）→ 降低单次帧数（8 → 4，接受更多调用）。

## 备选方案

**A. 自动帧识别（连通域 / 空白列检测）**
被否决。失败模式不可预测，且破坏了失败归因能力。

**B. 一维横向长条（1×N）**
被否决。8 帧长条比例 8:1，直接违反 API 的 3:1 约束。即使 4 帧（4:1）也超限。

**C. 每帧独立一次 API 调用**
被否决。这是 [PLAN §2.5](../PLAN.md) 明确反对的做法 —— 逐帧生成会导致服装、武器、比例和朝向漂移，且每一帧都要重传参考图（`gpt-image-2` 强制高保真处理输入图，这部分开销无法优化）。

**D. 混合方案：固定网格 + 内容微调**
被否决（暂时）。切分后再按内容边界微调每帧位置，听起来能兼顾两者，但引入了不确定性且收益有限 —— 后续的 `crop` + `bottom_center_align` 阶段本来就会按内容边界重新对齐，微调是多余的。
