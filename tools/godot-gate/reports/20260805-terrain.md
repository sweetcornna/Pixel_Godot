## 改坏再跑

两个反例都从上述正常 gate 工程复制，`expected.json` 保持不变，只改 `.tres` 中一个
被第五层读取的事实。每个坏工程均用与正常版相同的 Godot 命令运行。

### A：改一个 peering bit

唯一 diff：

```diff
-0:1/0/terrains_peering_bit/top_left_corner = 1
+0:1/0/terrains_peering_bit/top_left_corner = 0
```

Godot 退出 1：

```text
GATE-FAIL grass_dirt_corner/top_left peering bit 0 ≠ 1（grass）
```

### B：把 Corners 改成 Corners and Sides

唯一 diff：

```diff
-terrain_set_0/mode = 1
+terrain_set_0/mode = 0
```

mode 0 本身是合法值，所以 Godot loader **静默接受并成功加载资源**；这不是 Parse
Error。第五层通过 API 读回真实值后退出 1：

```text
GATE-FAIL terrain set 0 mode 0 ≠ 1（Corners）
```

因此 B 是有效反例：它确实改变 mode，且证明仅靠“加载成功”抓不住模式选错。

## unknown 路径

另复制资产，把 `grass_dirt_corner.measured_corners[0]` 改为 JSON `null` 后重新导出。
交付 notes 明示整块跳过；`.tres` 保留 `0:1/0 = 0`，但没有该格的 `terrain_set`、
`terrain` 或任何 peering bit。对应 expected 由修改后的 Manifest 生成，五层 gate 退出 0。

初版 gate 在该格直接调用 `get_terrain_peering_bit()`，Godot 会打印
`invalid peering bit` 后返回 `-1`，容易把错误日志误当通过证据。最终改用
`is_valid_terrain_peering_bit()`，确认四角均无效后再通过；最终日志干净。
